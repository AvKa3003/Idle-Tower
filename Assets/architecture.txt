Согласовано:
  [x] Строгое разделение Systems / Presenters / Views (вариант 2)
  [x] Тик-цикл: 10 тиков/сек (настраиваемо), баланс в секундах (GameDuration)

Ключевые решения:
  - Башня строго линейная (один столбец этажей снизу вверх), ветвления нет.
  - Функционал комнаты — не фиксирован: производство, свой UI, мини-игра и т.д.
  - Каждая комната ссылается на RoomBehavior (ScriptableObject) — плагин поведения.
  - Ядро знает только: построить, кликнуть, тикнуть, сохранить. Детали — в behavior.
  - Тик-цикл: частота тиков настраивается (плавность UI); баланс задаётся только в секундах.

Цель: расширяемая архитектура, в которой геймплей, UI и данные разделены.
Новые комнаты, ресурсы и экраны добавляются через ScriptableObject и префабы
без правки ядра систем.

1. ПРИНЦИПЫ
================================================================================

1.1 Разделение слоёв (строгое, вариант 2)
    Data → Systems → Presenters → Views

    Systems   — игровая логика; никаких ссылок на Canvas, Button, TMP.
    Presenters — единственный слой, который вызывает Systems и обновляет Views.
    Views     — только отображение: ссылки на UI, SetText/Show/Hide, без бизнес-логики.

    Правило: на каждую панель/экран — пара классов *Panel (View) + *Presenter.
    Исключений для «простых» попапов нет — единообразие важнее экономии файлов.

1.2 Конфиг через ScriptableObject
    Комнаты, ресурсы, дерево разблокировок — ассеты в Project, не хардкод в коде.

1.3 События состояния — GameEvents (статический Event Bus)

    Два канала (не смешивать):
    - Команды (клики): View → Presenter → System.Method()
    - Факты (состояние): System → GameEvents.Raise* → Presenter → View

    Реализация MVP: статический класс Scripts/Core/Events/GameEvents.cs
    - public static event + public static void Raise*(...) для каждого события
    - Публикуют ТОЛЬКО Systems после изменения данных
    - RoomBehavior → вызывает Systems (ResourceSystem.Add и т.д.), НЕ GameEvents напрямую
    - Подписываются Presenters в OnEnable, отписка в OnDisable

    События MVP (реализовать сразу):
    ┌──────────────────────────┬─────────────────────────┬──────────────────────────┐
    │ Событие                  │ Кто Raise               │ Кто слушает (MVP)        │
    ├──────────────────────────┼─────────────────────────┼──────────────────────────┤
    │ ResourceChanged          │ ResourceSystem          │ ResourceBarPresenter     │
    │   (resource, newAmount)  │ Add / TrySpend          │                          │
    │ RoomBuilt                │ BuildingSystem          │ TowerPresenter           │
    │   (roomIndex, room)     │ TryBuild успех          │                          │
    │ GameTick                 │ GameTickSystem          │ TowerPresenter (overlay) │
    │   (TickContext ctx)      │ каждый тик              │                          │
    │ ProductionModeChanged    │ RoomBehaviorSystem      │ TowerPresenter,          │
    │   (roomIndex, modeIndex)│ TrySetMode              │ ProductionModePresenter  │
    │ OperationModeUnlocked    │ RoomBehaviorSystem      │ ProductionModePresenter  │
    │   (roomIndex, modeIndex)│ TryUnlockMode           │                          │
    └──────────────────────────┴─────────────────────────┴──────────────────────────┘

    События отложены (заложить в коде как TODO / закомментированный шаблон):
    - ScreenChanged(ScreenId id) — когда появится 2+ экрана (Settings, Shop…)
      Raise из ScreenManager.Show; слушатели: скрыть/показать панели главного экрана

    UI после действия игрока (вариант A):
    - RoomSelectionPresenter: TryBuild → при успехе сам _panel.Hide()
    - ResourceBar / башня обновляются по ResourceChanged / RoomBuilt, не из RoomSelectionPresenter

    Расширение после MVP (рекомендации, не обязательно сразу):
    1) IGameEvents + GameEvents : IGameEvents — для unit-тестов без статики
    2) EventChannel SO (см. п. 9) — звук/VFX из Inspector
    3) Новое событие — только если ≥2 подписчика или слабая связность критична
    4) Не публиковать команды (BuildRoom, OpenPanel) — только факты состояния
    5) Аналитика: отдельный AnalyticsListener подписывается на GameEvents
    6) Оптимизация событий/UI (см. п. 9.1) — batch ResourceChanged, debounce отрисовки;
       в MVP: один Raise на каждый изменённый ресурс (TrySpend/Add), этого достаточно

1.3.1 EventChannel — отложено (напоминание)
    Файл EventChannel.cs НЕ пишем в MVP. Описание и сценарий — в разделе 9.

1.4 Единая точка входа
    GameBootstrap на сцене инициализирует сервисы и связывает их с вью.

1.5 Состояние игры отделено от отображения
    TowerState / SaveData — чистые данные. TowerView только отражает состояние.

1.6 Расширяемость
    - Новая комната = RoomDefinition.asset + RoomBehavior.asset + запись в BuildingTree
    - Новый ресурс = ResourceDefinition.asset
    - Новый тип функционала = новый класс RoomBehavior (наследник) + SO-ассет
    - Новый экран = IScreen + регистрация в ScreenManager (комната может на него ссылаться)

1.7 Линейная башня (фиксировано, без ветвления)
    - Один столбец этажей снизу вверх; на этаже — одна комната.
    - Ровно один build-slot сверху; геометрического ветвления нет и не планируется.
    - «Ветвление» только в выборе комнаты из разблокированных в UI постройки.
    - RoomDefinition.Behavior — ОБЯЗАТЕЛЬНО, без null; для декора — PassiveRoomBehavior (когда понадобится).
    - Класс (ProductionRoomBehavior.cs) = логика; .asset = параметры в Inspector (см. п. 1.7.1).
    - MVP production: отдельный behavior asset на каждую комнату (Production_Lumbermill, Production_Quarry).
    - Смена ProductionMode: у каждого режима свой ElapsedSeconds; при TrySetMode меняется только ActiveModeIndex.
    - SerializeState / DeserializeState — внутри каждого behavior, общего формата нет.

1.7.1 ScriptableObject и формат .asset
    - .cs  — код: алгоритмы, контракт IRoomBehavior, валидация.
    - .asset — YAML-файл Unity в Project; экземпляр SO с твоими настройками (modes, durations, icons).
    - Создание: ПКМ → Create → IdleTower → Production Room Behavior → Production_Lumbermill.asset
    - RoomDefinition ссылается на .asset через поле Behavior (перетаскивание в Inspector).
    - Зачем разделение: одна логика — много конфигов; баланс меняется без правки .cs; логика не смешана с полями Inspector.

1.7.2 Действия пользователя vs события состояния
    - Действия игрока (клик по комнате, слоту, кнопке): View → Presenter → прямой вызов System.
      Systems НЕ подписываются на клики через GameEvents.
    - События состояния: GameEvents → Presenters (см. п. 1.3)

1.8 Тик-цикл (Tick-based simulation)
    Частота тиков и баланс РАЗДЕЛЕНЫ:
    - TicksPerSecond (TPS) — настраиваемая «плавность» симуляции и UI; на баланс не влияет.
    - Все длительности в данных — в секундах (GameDuration), не в количестве тиков.

    Параметры (GameBalanceConfig):
    - int TicksPerSecond           — частота тиков (настраивается в asset при разработке); MVP: 10
    - float MaxCatchUpSeconds      — сколько секунд симуляции догоняем за один кадр (напр. 2.0)
    - int MaxTicksPerFrame         — вычисляется: TicksPerSecond * MaxCatchUpSeconds (10*2=20)

    Вычисляемые значения:
    - TickInterval = 1f / TicksPerSecond
    - При смене TPS пересчитывается только TickInterval; таймеры в секундах не сбрасываются.

    Алгоритм (GameBootstrap.Update):
    1) _accumulator += Time.deltaTime
    2) while (_accumulator >= TickInterval && ticksThisFrame < MaxTicksPerFrame):
         _accumulator -= TickInterval
         currentTick++
         TickContext: CurrentTick, TickDelta=TickInterval, TicksPerSecond, Services
         ITickable.OnTick в фиксированном порядке
         GameEvents.GameTick(ctx)
    3) Остаток _accumulator — для интерполяции UI (опционально)

    SimulationTimer (вместо счётчика тиков):
    - float elapsed в state поведения (у Production — ElapsedByMode[ActiveModeIndex])
    - каждый тик: elapsed += ctx.TickDelta
    - срабатывание: elapsed >= duration.TotalSeconds → действие, elapsed = 0
    - смена TPS 10→30: elapsed сохраняется → баланс в реальных секундах тот же

    GameDuration ([Serializable] struct):
    - int Minutes, int Seconds
    - float TotalSeconds => Minutes * 60f + Seconds
    - Пример: Minutes=0, Seconds=30 → 30 сек; Minutes=1, Seconds=30 → 90 сек
    - В Inspector задаёшь минуты и секунды; в коде везде TotalSeconds.

    currentTick (ulong) — счётчик тиков (отладка, save, аналитика); не использовать для баланса.

    Офлайн (позже):
    - elapsedWallSeconds = now - lastSaveTime
    - SimulateForSeconds(elapsedWallSeconds) — тики без лимита MaxTicksPerFrame, без UI

3. МОДЕЛЬ ДАННЫХ
================================================================================

3.1 ResourceDefinition (ScriptableObject)
    - string Id
    - string DisplayName
    - Sprite Icon

3.2 IRoomBehavior / RoomBehaviorBase (ScriptableObject)
    Контракт — ядро вызывает только эти методы; внутри — любая логика:

    - OnRoomBuilt(RoomBehaviorContext ctx)
    - OnRoomClicked(RoomBehaviorContext ctx) → RoomClickResult
        RoomClickResult: { RoomUiId? OpenUi } — behavior не открывает UI сам
    - Tick(TickContext ctx)
    - CreateDefaultState() → RoomBehaviorState
    - SerializeState / DeserializeState — формат свой у каждого behavior
    - GetRoomStatusInfo(ctx) → RoomStatusInfo (MVP overlay на RoomView)

    RoomStatusInfo (для overlay в MVP):
    - Sprite OutputIcon               — иконка первого OutputPerCycle (MVP)
    - string ModeLabel              — «Дерево», «Камень»
    - int AmountPerCycle            — количество первого OutputPerCycle (MVP)
    - ResourceCost[] OutputPerCycle — полный список выхода (для UI с несколькими иконками позже)
    - float Progress01              — ElapsedSeconds / CycleDuration (0..1)
    - float ElapsedSeconds, float CycleTotalSeconds — для текста «2.1 / 3.0»

    ProductionBehaviorState:
    - Dictionary<int, float> ElapsedByMode   — прогресс цикла отдельно для каждого modeIndex
    - int ActiveModeIndex
    - List<int> UnlockedModeIndices
    При TrySetMode: ActiveModeIndex меняется; ElapsedByMode не трогается — прогресс режимов сохраняется по отдельности.
    Tick и overlay читают/пишут ElapsedByMode[ActiveModeIndex] (через ActiveElapsedSeconds).

    RoomUiId (enum, расширяется при новом UI):
    - None
    - ProductionMode              — выбор режима производства
    - Shop                        — (позже)

    Реализации:
    - ProductionRoomBehavior  — production; отдельный .asset на комнату (modes в asset)
    - OpenUiRoomBehavior      — OnRoomClicked → OpenUi = Shop
    - PassiveRoomBehavior     — заглушка; создать когда понадобится декор

3.3 RoomDefinition (ScriptableObject)
    - string Id
    - string DisplayName
    - Sprite Icon
    - GameObject Prefab
    - ResourceCost[] Cost
    - RoomBehaviorBase Behavior    — ОБЯЗАТЕЛЬНО: определяет функционал комнаты
    - UnlockRule[] UnlockRules

3.4 OperationMode (ProductionMode.cs — производство и крафт это одно)
    Термин: «операция» = цикл на этаже. Без входа = производство; с входом = крафт.

    - string Id, DisplayName, Icon
    - ResourceCost[] OutputPerCycle      — выдача за цикл (один или несколько ресурсов); пусто = нет выхода
    - GameDuration CycleDuration
    - ResourceCost[] InputPerCycle       — потребление за цикл; пусто = бесплатное производство
    - ResourceCost[] UnlockCost          — разовая оплата, чтобы режим стал доступен; пусто = открыт сразу
    - UnlockRule[] UnlockRules           — условия видимости (AND), как у комнат; опционально
    - bool UnlockedByDefault             — true для стартового режима (обычно modes[0])

    Цикл Tick (каждый вызов behavior.Tick) — одна операция для производства и крафта:

    - canAfford = InputPerCycle пуст → true; иначе CanAfford(InputPerCycle)
    - SimulationTimer.AdvanceCycle(elapsed, TickDelta, CycleDuration, canAfford) → bool cycleComplete
    - если !canAfford → ElapsedByMode[active] = 0 каждый тик (сброс прогресса крафта)
    - если cycleComplete → TrySpend(InputPerCycle) при непустом входе → Add(OutputPerCycle) → elapsed = 0
    - Когда ресурсов снова хватает — таймер крафта набирается с нуля

    Overlay: Progress01 = 0 пока canAfford == false (цикл сброшен).

    Разблокировка режима (отдельно от выбора активного):
    - TryUnlockMode(roomIndex, modeIndex): UnlockRules ✓, ещё не unlocked, CanAfford(UnlockCost)
      → TrySpend(UnlockCost) → добавить modeIndex в UnlockedModes в state
    - TrySetMode(roomIndex, modeIndex): mode уже unlocked → ActiveModeIndex; прогресс других режимов не меняется

    ProductionBehaviorState:
    - Dictionary<int, float> ElapsedByMode — отдельный таймер на каждый режим
    - int ActiveModeIndex
    - List<int> UnlockedModeIndices   — modes[0] в OnRoomBuilt всегда

3.4.1 GameDuration
    - int Minutes, int Seconds
    - float TotalSeconds
    Используется везде, где в балансе есть время: производство, кулдауны, бафы.

3.5 UnlockRule (разблокировка для списка ПОСТРОЙКИ)
    Типы (enum UnlockRuleType):
    - AlwaysAvailable           — комната всегда в списке (если ещё не построена)
    - RequiresRoomBuilt         — на башне есть этаж с указанным RoomDefinition

    Логика нескольких правил на одной комнате: AND (все должны выполниться).
    RequiresResourceAmount — не используется.

    Уникальность: каждый RoomDefinition можно построить на башне только 1 раз.
    Повтор «той же» комнаты в late game — отдельный RoomDefinition в BuildingTreeConfig
    (копия с новым Id, своими UnlockRules, своим Cost); может требовать уже построенную
    «оригинальную» комнату через RequiresRoomBuilt.

    Пример дубликата:
    - room_lumbermill        — AlwaysAvailable, строится 1 раз
    - room_lumbermill_t2     — RequiresRoomBuilt(room_lumbermill) + другие rules,
                               отдельный asset, тот же prefab/behavior или свой

3.6 BuildingTreeConfig (ScriptableObject)
    - RoomDefinition[] AllRooms — полный реестр комнат для UnlockTreeSystem

    «Дерево» — логическое: связи через RequiresRoomBuilt между RoomDefinition.
    Геометрия башни линейная; ветвление — в выборе, какую из разблокированных комнат строить.

3.6.1 Разделение Unlock vs Cost
    - UnlockRules  — комната попадает в список UI (UnlockTreeSystem)
    - Cost         — хватает ли ресурсов (BuildingSystem.CanAfford)
    Заблокированные (rules не выполнены) — не показываются в UI.
    Разблокированные без ресурсов — показываются dim / «недоступно для постройки».

3.7 TowerState (runtime)
    - List<TowerRoom> Rooms
    TowerRoom:
    - RoomDefinition BuiltRoom      — null у пустой комнаты (слот строительства сверху)
    - RoomBehaviorState State       — произвольные данные поведения (режим, прогресс, флаги)
    - bool IsEmpty => BuiltRoom == null

    Инвариант: линейная башня, одна пустая комната сверху (EmptyRoomIndex).

3.8 ResourceWallet (runtime)
    - Dictionary<string, int> по ResourceDefinition.Id

3.9 RoomBehaviorContext (runtime, не сохраняется)
    - int RoomIndex
    - TowerRoom TowerRoom
    - TowerState Tower
    - GameServices Services
    Передаётся в каждый вызов behavior — доступ к ресурсам, UI, событиям без жёсткой связи.

4. СИСТЕМЫ И ОТВЕТСТВЕННОСТЬ
================================================================================

4.0 GameTickSystem
    Параметры — см. п. 1.8. Кратко:
    - TicksPerSecond — только в GameBalanceConfig (при разработке)
    - MaxTicksPerFrame = TicksPerSecond * MaxCatchUpSeconds (при TPS=10, CatchUp=2с → 20)
    - SimulateForSeconds(float) — офлайн, без MaxTicksPerFrame

    Порядок ITickable на тик (RegisterTickable):
    1) RoomBehaviorSystem
    2) (будущие: BuffSystem, QuestSystem…)
    3) SaveSystem (позже)

    ITickable vs Scripts/Systems/:
    - ITickable (Core) — только то, что вызывается каждый тик из GameTickSystem
    - ResourceSystem, BuildingSystem, UnlockTreeSystem — сервисы по запросу через
      GameServices; ITickable не реализуют
    - RoomBehaviorSystem — и сервис (GameServices.RoomBehaviors), и ITickable
    - Инициализация игры — GameServices.InitializeNewGame(), не ITickable

4.1 ResourceSystem
    CanAfford, TrySpend, Add; Raise ResourceChanged после изменения кошелька.
    MVP: при TrySpend/Add с несколькими ResourceCost — отдельный Raise на каждый
    ресурс (простота; оптимизация batch — п. 9.1, фаза 6).

4.2 UnlockTreeSystem
    - GetAvailableRooms(TowerState) → RoomDefinition[]
      1) Перебор BuildingTreeConfig.AllRooms
      2) Пропуск, если этот RoomDefinition уже построен на башне (уникальность)
      3) Пропуск, если не все UnlockRules выполнены (AND)
      4) AlwaysAvailable: правило всегда true; такие комнаты в списке с самого начала
         (пока не построены — см. шаг 2)

    - IsAvailable(RoomDefinition room, TowerState) → bool
      Те же проверки; используется в BuildingSystem.TryBuild

    - EvaluateRule(UnlockRule, TowerState) → bool
      AlwaysAvailable → true
      RequiresRoomBuilt → tower содержит построенную комнату room.RequiredRoom

4.3 BuildingSystem
    - TryBuild(roomIndex, RoomDefinition) → BuildResult
      1) roomIndex — индекс пустой комнаты сверху (EmptyRoomIndex)
      2) UnlockTreeSystem.IsAvailable(room, tower)
      3) ResourceSystem.CanAfford(room.Cost) — иначе отказ
      4) ResourceSystem.TrySpend(cost)
      5) Записать тип комнаты, добавить новую пустую комнату сверху
      6) RoomBehaviorSystem.OnRoomBuilt(roomIndex)
      7) GameEvents.RoomBuilt
    - CanAfford(room) → bool — только ресурсы (для dim в UI)

4.4 RoomBehaviorSystem (ITickable + сервис)
    - OnTick(TickContext ctx)
    - OnRoomClicked(int roomIndex) → RoomClickResult
    - OnRoomBuilt(int roomIndex)
    - TryUnlockMode(roomIndex, modeIndex) → bool   — разовая оплата UnlockCost
    - TrySetMode(roomIndex, modeIndex) → bool      — выбор активного (только unlocked)
    - GetOperationModes(roomIndex) → список для UI (locked/unlocked/active, costs)
    - GetRoomStatusInfo(roomIndex) → RoomStatusInfo

4.5 ProductionRoomBehavior
    - OnRoomBuilt: modes[0] → UnlockedModes; ActiveModeIndex = 0
    - Tick: логика производства/крафта (см. п. 3.4); сброс ElapsedByMode[active] при нехватке InputPerCycle
    - OnRoomClicked: если modes.Length > 1 или есть незакрытые unlock → OpenUi = ProductionMode
    - SerializeState: ElapsedByMode, ActiveModeIndex, UnlockedModeIndices

4.6 OpenUiRoomBehavior (пример behavior)
    - OnRoomClicked → RoomClickResult { OpenUi = RoomUiId.Shop }
    - TowerPresenter → ShopPresenter.OpenForRoom(roomIndex)
    - OnTick: пусто

4.7 ScreenManager
    (без изменений — экраны открываются и с главного меню, и из комнат)

4.8 SaveSystem
    - Сохраняет currentTick + TowerState + Wallet (для офлайн-симуляции позже)
    - Сохраняет TowerState.Rooms[].State через behavior.SerializeState
    - При загрузке — behavior.DeserializeState

6. UI И ПРЕЗЕНТЕРЫ (строгий вариант 2)
================================================================================

Паттерн: каждый UI-модуль = View + Presenter (всегда пара).

View (*Panel, *View, *Screen):
  - MonoBehaviour со ссылками на UI-элементы
  - Публичные методы отображения: SetRooms(), SetAmount(), Show(), Hide()
  - События клика наружу: C# event / UnityEvent → Presenter (не в System!)
  - НЕ вызывает GameServices, BuildingSystem, ResourceSystem

Presenter (*Presenter):
  - Действия игрока: прямой вызов Systems (BuildingSystem, RoomBehaviorSystem…)
  - Изменения состояния: подписка на GameEvents (ResourceChanged, RoomBuilt, GameTick)
  - Маршрутизация RoomUiId → нужный Presenter (TowerPresenter → ProductionModePresenter)

Связка в сцене:
  - Presenter и View на одном GameObject или Presenter ссылается на View через SerializeField
  - GameBootstrap / Screen не связывает View с Systems напрямую

Обязательные пары для MVP:
  - ResourceBarPanel        + ResourceBarPresenter
  - RoomSelectionPanel      + RoomSelectionPresenter
  - MainTowerScreen         + MainTowerPresenter (или TowerPresenter для башни)
  - TowerView               + TowerPresenter
  - EmptyRoomView / RoomView — клики → TowerPresenter (прямой вызов или C# event на Presenter)

UI поведений комнат (строго):
  - ProductionModePanel + ProductionModePresenter
  - Behavior возвращает RoomUiId в RoomClickResult; TowerPresenter открывает нужный Presenter
  - RoomBehavior НЕ открывает Canvas

Структура папок UI:
  UI/
    Views/       — *Panel, *View, *Screen (только отображение)
    Presenters/  — вся логика привязки UI ↔ Systems
    Presenters/Rooms/  — презентеры UI конкретных RoomBehavior

ScreenManager:
  - Переключает IScreen (View); Presenter экрана активен вместе с View
  - Canvas: активен один экран; Presenter подписан пока экран виден

9.1 Оптимизация событий и отрисовки UI (после MVP, фаза 6)
  Сейчас (MVP): ResourceSystem вызывает RaiseResourceChanged на каждый ресурс в
  TrySpend/Add; Presenter обновляет View при каждом Raise. Для 4 ресурсов и редких
  трат/крафта — нормально, не оптимизируем.

  Позже (если лаги или много ресурсов за одну операцию):
    - Batch: ResourcesChanged(ResourceDefinition[] или snapshot кошелька) — один Raise
      после TrySpend/Add вместо N вызовов ResourceChanged
    - Debounce UI: Presenter помечает dirty на событиях, полный Refresh на GameTick
      или в LateUpdate (один проход за кадр)
    - Разделить: GameTick — overlay/прогресс; ResourceChanged batch — полоска ресурсов

  Не делать до стабильного MVP без измеренной проблемы.

- Новый RoomBehavior: крафт, бои, квесты — отдельный SO + класс
- Доп. ProductionMode — только данные в ProductionRoomBehavior
- Офлайн-доход: GameTickSystem.SimulateForSeconds(elapsed) без лимита кадра
- Мета-прогресс, престиж: отдельные системы + SaveSystem
- Addressables для комнат: RoomDefinition загружает prefab по address
- Localization: DisplayName через Localization Package
- Аналитика: подписчик на GameEvents без изменения систем
